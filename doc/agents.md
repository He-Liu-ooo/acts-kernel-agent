# Agents — `src/agents/`

3 LLM agents built on the OpenAI Agents SDK. No separate Debugger — the Coder handles self-correction via tools.

## Architecture

```
Planner (submit-only: one `submit_plan` tool, no compile/correctness loop)
    → Coder (tool-using: compile + correctness)
        → [orchestrator-side eval]
            → Reviewer (submit-only by default: one `submit_review` tool; optional `query_metric` tool when `reviewer_metric_queries=True`)
```

The deterministic orchestrator controls all flow. Agents are stateless — caller-facing each `plan()` / `review()` looks like one logical run, but the SDK loop may take multiple turns: Planner / Reviewer route their structured submission through a `submit_*` tool (and the Reviewer can optionally fetch additional metrics via `query_metric` before submitting); Coder runs a multi-tool compile/correctness loop before its `submit_kernel` call.

## Planner — `planner.py`

**Role**: Analyzes profiling data + optimization memory, selects technique from action library, produces structured plan.

**SDK pattern**: One logical call from the caller's view, but tool-backed inside the SDK loop (the agent may take multiple turns to land its `submit_plan` invocation). `Agent(name="Planner", instructions=..., model=..., tools=[submit_plan])` is built fresh per `plan()` call (no compile/correctness loop — `submit_plan` is the only tool) → `Runner.run(..., max_turns=4)`. The submit tool replaces the `output_type=Pydantic` enforcement that the SDK used to translate to a `response_format=json_schema` API field — that field is rejected by reasoning-model providers (DeepSeek-reasoner, etc.), so the Planner routes its structured submission through a tool call instead, mirroring the Coder. Tool-call schemas are universally supported across OpenAI-compatible providers; the same Pydantic validator runs inside the tool body, preserving the "validation failure → in-loop retry" guarantee.

- `submit_plan(tier, technique, params=None, target_region="", rationale="")` — required Python args (`tier`, `technique`) match `OptimizationPlanOutput`'s required Pydantic fields; optional args with defaults match the Pydantic-optional fields. The tool body instantiates `OptimizationPlanOutput(...)` (triggering validation) and stores the result in a per-call captured dict. On validation failure the tool returns `submit_plan FAILED:<error>` so the SDK hands the error back to the LLM as the tool-call response, prompting an in-loop retry within the turn budget.
- Tool registered with `function_tool(_make_submit_plan_tool(...), strict_mode=False)`: the SDK's strict-schema validator rejects `dict[str, X]` (the `params` arg) with the same `additionalProperties should not be set` UserError that originally killed the `output_type=Pydantic` path. `strict_mode=False` skips that pre-flight check; Pydantic still validates inside the tool body, so end-to-end type safety is preserved and malformed payloads bounce through the in-loop retry budget.
- `max_turns=4` reserves room for one in-band validation retry (initial submit attempt + corrective resubmit + headroom for the final plain-text confirmation), keeping the Planner cheap while still leaving the LLM a chance to self-correct a malformed submission.
- `MaxTurnsExceeded` recovery: the captured dict is preferred — if a valid submission landed before the budget ran out, `_validate_and_convert` returns the corresponding `OptimizationPlan`. If the dict is empty, `PlanningError` is raised.

**Output models**:
- `OptimizationPlanOutput` (Pydantic) — validated inside `submit_plan`'s tool body. Fields: `tier` (int, required), `technique` (str, required), `params` (dict, optional), `target_region` (str, optional), `rationale` (str, optional).
- `OptimizationPlan` (dataclass) — internal representation used by the rest of the codebase. Converted from `OptimizationPlanOutput` via `_validate_and_convert()` (which also enforces the available-actions guard).

**Prompt assembly**: `build_user_prompt()` (static method) assembles the user prompt from runtime data. Sections, in order: Current kernel (with backtick escaping), **Run context** (once-per-run bottleneck via shared `render_run_context()` helper — omitted when no `bottleneck` is supplied), Profiling summary, Past experiences (with action parameters), Available actions, Search tree context, **Siblings already tried from this parent** (sibling-aware feedback — rendered between `## Search tree context` and `## Reviewer feedback`, omitted when the kwarg is empty), Reviewer feedback. Empty sections are omitted. When the parent node has a stored `last_review`, the orchestrator passes a curated render (outcome / bottleneck_diagnosis / suggestions / conditional_assessment) via `_render_review_for_planner` from `reviewer.py`. None on the iter-1 root expansion unless the Phase-A baseline review pass populated `root.last_review`. Planner receives the **condensed** parent source — orchestrator calls `Kernel.render_condensed_source(representative_workload_uuid=workloads[0].uuid)` so the `@triton.autotune` decorator block is replaced by a `# autotune:` summary line (and a `# winner ...` line when available). See `doc/kernels.md`'s `render_condensed_source` subsection.

The `sibling_context: str = ""` kwarg on both `build_user_prompt()` and `plan()` carries the rendered per-sibling one-liners (action, params, SOL, Δ vs parent, outcome, branch_quality) from `SearchTree.render_siblings(parent.id)` — see `doc/search.md` for the rendering contract. Default empty preserves the iter-1 / single-child-parent call sites that have no sibling history; section is gated `if sibling_context:` so an empty kwarg cleanly omits the section.

**Input** (via orchestrator): kernel source, profiling summary (from Reviewer), past experiences (from MemoryRetriever), available actions (filtered list per run from `ActionRegistry.list_applicable(kernel_type, hardware=self._config.hardware)` — see Validation below), tree context, `bottleneck: BottleneckType | None` (the run-level classification; threaded verbatim from `SearchResult.run_bottleneck`), `sibling_context: str = ""` (rendered sibling history from `SearchTree.render_siblings(parent.id)` — empty on iter-1 / single-child-parent expansions).

**Output**: `OptimizationPlan` — `{tier, technique, params, target_region, rationale}`.

**Error handling**: `PlanningError` is raised when: (1) `run_agent()` returns `None` (all retries exhausted), (2) the LLM returns a technique not in `available_actions`, or (3) SDK `MaxTurnsExceeded` fires without a captured submission. `MaxTurnsExceeded` is caught at the agent boundary — if a valid submission landed before the budget exhausted, the captured output is converted to an `OptimizationPlan` and returned; otherwise it's converted to `PlanningError` so the orchestrator has a single typed failure to catch. The orchestrator's iteration loop catches `PlanningError` branch-locally (skip-iter, decay epsilon, increment `parent.consecutive_agent_failures`, emit `planner_failed`) — no longer aborts the run. Without a model configured, returns a default plan (no LLM call).

**Validation**: The selected technique must be in `available_actions`. The orchestrator builds this list per run from `build_default_registry().list_applicable(kernel_type, hardware=self._config.hardware)` so it is always non-empty in production paths — the guard is always active and rejects both hallucinated technique IDs and catalog actions that don't apply to the current `kernel_type` / hardware combo (e.g., Hopper-only Tier-5 actions on an Ada device). Tests and placeholder / baseline call sites may still pass an empty list, in which case the guard short-circuits to a pass — kept this way so `_validate_and_convert` stays usable in those paths.

**System prompt** (`prompts/planner/system.md`): Bottleneck→technique mapping tables (memory_bound, compute_bound, balanced), expected gains by tier, experience interpretation guide, 8 anti-patterns, 7 decision rules. The "You receive" list enumerates the prompt sections the orchestrator threads in, including `Siblings already tried from this parent` (item 7 — present from iter 2 onward when the parent has been expanded more than once). Sibling-aware rules:
- Decision rule **"Use sibling history"**: a sibling regression (Δ SOL < −0.02) on an action from this parent forbids re-picking that action unless the Reviewer's current diagnosis cites a metric-chain reason for a specific param change. Sibling history is per-branch evidence and outranks `## Past experiences` (cross-run).
- Anti-pattern **"Re-picking a sibling's failed action without a metric-grounded reason"** — paired with the decision rule above; rules out the "different param, same action" reflex when the Reviewer didn't tie the param to a metric.

**Model choice**: Strongest reasoning model (planning quality is the bottleneck).

**Private surface**:
- `_make_submit_plan_tool(captured: dict) -> Callable[..., str]` — closure factory that returns the `submit_plan` tool body bound to a per-call captured dict. The tool body validates `OptimizationPlanOutput(**kwargs)`; on success it stores the validated output in `captured` and returns a sentinel string for the LLM to confirm; on failure it returns `submit_plan FAILED:<error>` so the SDK hands the error back for in-loop retry. Factory is unit-testable without the SDK.
- `_validate_and_convert(out, available_actions) -> OptimizationPlan` — converts a captured `OptimizationPlanOutput` into the internal dataclass and enforces the available-actions guard (raises `PlanningError` on hallucinated technique IDs).
- `has_model` property — `self._model is not None and _SDK_AVAILABLE`. Returns `False` even when a model stub is attached if the SDK isn't importable, so callers branch correctly without touching `_model` directly.
- `parse_plan` removed — Pydantic validation runs inside the tool body, so no out-of-loop parser is needed.

## Coder — `coder.py`

**Role**: Implements the Planner's plan into kernel code. Self-corrects compilation and correctness errors via tools, then emits its final answer via a submit-tool call.

**SDK pattern**: Tool-using, no `output_type=`. `Agent(name="Coder", instructions=..., model=..., tools=[compile_kernel_tool, check_correctness_tool, submit_kernel])` → `Runner.run()` with an internal tool loop bounded by `max_turns`. The submit tool replaces the `output_type=Pydantic` enforcement that the SDK used to translate to a `response_format=json_schema` API field — that field is rejected by reasoning-model providers (DeepSeek-reasoner, etc.), so the Coder routes its structured submission through a tool call instead. Tool-call schemas are universally supported across OpenAI-compatible providers; same Pydantic validator runs inside the tool body, preserving T4's "validation failure → in-loop tool retry" guarantee verbatim.

**Output model**:
- `KernelCodeOutput` (Pydantic) — `source_code: str` plus `triton_kernel_name: str`, with a `@model_validator(mode="after")` that pulls every `@triton.jit def <name>` out of `source_code` and asserts the declared name is one of them. Validation runs inside `submit_kernel`'s tool body; on failure the tool returns the validator's error string and the SDK hands it back to the LLM as the tool-call response, prompting an in-loop retry within the existing turn budget. The `triton_kernel_name` field is consumed downstream by `eval/profiler.py` as the highest-priority source for NCU's `--kernel-name regex:` filter — explicit declaration removes the silent mis-profiling failure mode that source-regex extraction had on fused kernels with multiple `@triton.jit` defs.
- A second `@model_validator(mode="after")` named `_autotune_decorator_well_formed` enforces that every Coder-emitted source carries a well-formed `@triton.autotune` decorator on the kernel named by `triton_kernel_name`. Three rules: (1) a `@triton.autotune(...)` decorator must sit directly above the `@triton.jit def <triton_kernel_name>(...)` line; (2) the decorator's `configs=[...]` list must contain ≥4 `triton.Config(...)` entries; (3) the decorator's `key=[...]` list must be present and non-empty. Failure surfaces through the same `submit_kernel` tool-response path as the kernel-name validator — the SDK hands the error back to the LLM for an in-loop retry within the existing turn budget; no new retry machinery. The matching LLM-facing contract lives in `src/prompts/coder/translate.md` and `src/prompts/coder/implement.md` under their `## Autotune` sections, which spell out the three rules plus an example decorator shape so the model knows what the validator enforces. See `doc/specs/2026-05-14-a1-triton-autotune-design.md` §1.2 + §1.3 for the design rationale.

**Tools** (built per call via `_make_compile_tool` / `_make_correctness_tool` / `_make_submit_tool`, then wrapped with `@function_tool` at Agent-construction time so the factories stay unit-testable without the SDK). All three factories accept a keyword-only `error_log: list[str] | None = None`: when non-None, every FAILED return is appended via the shared `_record_failure(error_log, msg)` helper so cross-turn errors can ride out of the SDK loop as `ImplementationError.tool_errors`. Success returns are never logged — they aren't failures to remember. The submit-tool case is load-bearing for accurate cross-attempt rendering: an attempt that fails only at submit-time has no compile / correctness errors to recall, so without logging submit-validation failures the next attempt's prompt would show the misleading "no tool errors recorded" placeholder.
- `compile_kernel_tool(source_code)` → calls `kernels/compiler.py::compile_kernel`. Success returns an entrypoint confirmation; failure returns the full compiler traceback so the Coder can read the error and fix it.
- `check_correctness_tool(source_code)` → recompiles the candidate (compile is cheap) and runs `eval/correctness.py::verify_correctness` against **every** input generator bound at call time, short-circuiting on the first failure. Returns a human-readable pass/fail message that names the failing workload index and stage. Compile failures are surfaced before attempting correctness so the Coder gets the cheaper error first.
- `submit_kernel(source_code, triton_kernel_name)` → instantiates `KernelCodeOutput(...)` (triggers the cross-field validator) and stores the validated output in a per-call captured dict. Success returns a sentinel string instructing the LLM to emit a one-word confirmation so the SDK loop terminates; validation failure returns the error string for an in-loop retry. After `_run_tool_agent` returns, an empty captured dict raises `ImplementationError("Coder did not call submit_kernel ...")` — fail-loud rather than silently treating a missing submission as a degraded best-effort.

**Per-call binding**: both tools are closures over `(kernel_spec, reference_fn, input_generators)` captured when `implement()` or `translate()` is invoked. A fresh `Agent` is constructed per call — cheap (object construction, no network) and keeps the oracle bound to the right problem.

**Prompt assembly**: `build_user_prompt()` (static method) assembles the user prompt from the kernel source and the `OptimizationPlan`. Sections: Current kernel (via shared `render_kernel_section()` helper — backticks escaped), Optimization plan (tier, technique, optional params, target region, rationale). **Reviewer feedback is intentionally not included** — the Planner has already consumed it and distilled its conclusions into the plan, so the Coder works from the plan only.

**Turn budget**: `self._max_turns = 2 * config.max_debug_retries + 2` — derived at construction time from `ACTSConfig`. Derivation: `max_debug_retries` compile+correctness tries × 2 tool turns per cycle + 1 `submit_kernel` tool call + 1 final plain-text confirmation. Default config (`max_debug_retries=3`) gives 8. The one sanctioned failure mode, spelled out in `system.md`, is calling `submit_kernel` with the last version that compiled cleanly when the budget runs out without a green correctness run.

**`has_model` property**: `True` when the agent is backed by a real LLM. Callers that must branch before reaching into internals (e.g., `baseline_generator` fail-closing without a model) use this instead of touching `_model` directly.

**Entry points**:

`implement(kernel_source, plan, *, kernel_spec, reference_fn, input_generators) -> KernelCodeOutput` — the per-iteration call from the orchestrator. Applies the plan to the current kernel; `kernel_spec` + `reference_fn` + `input_generators` (one generator per selected workload) are jointly required when a model is configured — all three are captured by the tool closures. Without a model configured, returns a `KernelCodeOutput.model_construct(source_code=<unchanged>, triton_kernel_name="")` stub (validation skipped — no LLM produced the source, so the empty kernel name signals to the profiler to use its regex fallback).

`translate(*, reference_source, kernel_spec, reference_fn, input_generators, prior_failures=()) -> KernelCodeOutput` — one-shot PyTorch→Triton port used at problem-load time by `benchmark/baseline_generator.py`. Drives the same tool-loop as `implement()` (shared via `_run_tool_agent`) but under a dedicated system prompt (`prompts/coder/translate.md`) that emphasizes signature invariance and no precision drop. Callers post-verify after translation because the SDK may emit a degraded best-effort when the turn budget is exhausted. No no-op fallback — raises `ImplementationError` when no model is configured, since there is no sensible from-scratch port without an LLM. The keyword-only `prior_failures: Sequence[AttemptFailure] = ()` is forwarded to `build_translate_prompt`; non-empty values surface what didn't work in earlier baseline-generation attempts for the same reference (see "Cross-attempt memory" below). Empty default keeps the call site backward-compatible.

**Translate prompt assembly**: `build_translate_prompt(reference_source, kernel_spec, *, prior_failures=())` is a separate static method (backticks in the reference are escaped, target kernel name/entrypoint/kernel-type are surfaced) so the PyTorch→Triton port prompt is distinct from the per-iteration `implement()` prompt format. When `prior_failures` is non-empty, a `## Prior attempt failures` section is prepended *before* `## PyTorch reference` so the model sees the retry history first; each `AttemptFailure` renders as `### Attempt N` with one bullet per tool-error string. An attempt with empty `tool_errors` (the agent never invoked compile / correctness / submit — typically a reasoning-content budget issue) renders an explicit placeholder so recurring "silent" attempts are still visually distinct in the prompt. Per-attempt sub-headers are load-bearing: when the same error class recurs across attempts, the visual repetition is the signal that tells the model to try a structurally different approach rather than re-applying the same kernel + same fix.

**Output**: `KernelCodeOutput` carrying both `source_code` and the validated `triton_kernel_name`; downstream callers (orchestrator, baseline_generator) thread both fields into the new `Kernel`. **May be a degraded best-effort** when the SDK tool loop exhausts `max_turns` without a green correctness run — downstream verification/scoring (or, for `translate()`, the caller's post-verify pass) handles that case.

**Error handling**: `ImplementationError` is raised when `run_agent()` returns `None` (transient retry exhaustion), when `translate()` is called without a model, when `implement()` is called with a model but missing correctness context (`kernel_spec` / `reference_fn` / a non-empty `input_generators`), when the LLM exits the tool loop without ever calling `submit_kernel`, or when SDK `MaxTurnsExceeded` fires without a prior submission. SDK `MaxTurnsExceeded` is converted to `ImplementationError` at the Coder boundary (option γ, 2026-04-22) so callers have a single typed failure to catch — if a valid submission landed before the budget exhausted, the captured output is returned instead. The orchestrator's iteration loop catches `ImplementationError` and skips the iteration (logs warning, decays epsilon, continues); `baseline_generator.py`'s 3-attempt retry loop handles the same exception during Phase A. The exception carries a `tool_errors: list[str]` attribute (`__init__` accepts a keyword-only `tool_errors=None` defaulting to `[]`) — the chronological list of FAILED strings the compile / correctness / submit tools returned during the SDK loop, threaded into the next attempt by `baseline_generator` (see "Cross-attempt memory" below). Existing `ImplementationError("msg")` raise sites stay backward-compatible — the kwarg defaults to an empty list.

**Cross-attempt memory**: when `baseline_generator.generate_triton_baseline` retries after an `ImplementationError`, it threads the prior attempts' tool errors into the next `translate()` call so the Coder's prompt can surface what didn't work — preventing the model from re-emitting the same kernel + same error across `Runner.run` boundaries. The agent surface for that is:
- `AttemptFailure` — frozen dataclass colocated with `ImplementationError` in `coder.py`. Fields: `attempt_no: int` (1-indexed, matches `emit()` event payloads on the pipeline side) and `tool_errors: list[str]` (chronological FAILED tool returns observed during the attempt; empty when no tool calls happened). Imported and constructed by `baseline_generator` after each catch and forwarded back into `CoderAgent.translate(..., prior_failures=...)`.
- `_run_tool_agent` binds one `tool_errors: list[str]` list and passes it as `error_log=tool_errors` to all three factory calls (`_make_compile_tool` / `_make_correctness_tool` / `_make_submit_tool`), so every tool's FAILED return appends to the same list. The three `ImplementationError` raise sites in `_run_tool_agent` (`MaxTurnsExceeded` recovery, no-submit, `LLM call failed`) all carry `tool_errors=tool_errors` out, so cross-attempt memory survives every Coder-side failure mode.
- Inclusion of the submit-tool case in this wiring is what keeps cross-attempt rendering honest. An attempt that fails only at submit-time (compile + correctness both passed, but the LLM's final payload tripped the `KernelCodeOutput` validator) would otherwise carry `tool_errors=[]` and render the misleading "no tool errors recorded" placeholder in the next attempt's prompt. With the submit-tool's `error_log` wired, the validator's error string lands in the list and the next attempt sees the real reason it failed.

**Temperature**: 0.0. Determinism is load-bearing for code generation — variance in kernel code is almost always noise, not creativity. Planner/Reviewer use 0.3 for exactly the opposite reason (see Planner / Reviewer sections). All three per-agent values are overridden when `ModelConfig.force_temperature` is set: `make_run_config` in `llm_backend.py` reads the module-level `_FORCE_TEMPERATURE` populated by `load_model_config` and pins every agent to that value. Required for reasoning-style models that reject anything other than a fixed temperature (Kimi-K2, OpenAI o-series, DeepSeek-Reasoner / -v4-pro — all locked to 1.0). When `force_temperature` is `None`, per-agent values are used unchanged. The Planner / Reviewer sections do not repeat this — treat this paragraph as canonical.

**System prompt** (`prompts/coder/system.md`): prescribed 6-step workflow (apply change → compile → correctness → submit → confirm), hard rules (signature invariance, `triton_kernel_name` matches source, one focused change, no benchmarking, no bypassing correctness, no invented APIs, no precision drop, no stray imports), anti-patterns (rewrites, correctness-before-compile, snippets, prose in submitted source, multi-change after failure, calling more tools after submit). The hard rule on correctness bypassing explicitly defines the single legal failure-mode submission so the prompt and the `KernelCodeOutput` schema never contradict each other.

**Model choice**: Strong code + reasoning model.

## Reviewer — `reviewer.py`

**Role**: Interprets eval results into structured feedback. Acts as intelligent filter between raw profiling data and the Planner.

**SDK pattern**: One logical call from the caller's view, tool-backed inside the SDK loop — same shape as the Planner; the agent may take multiple turns to land its `submit_review` invocation (and, when `reviewer_metric_queries=True`, can interleave `query_metric` fetches first). `Agent(name="Reviewer", instructions=..., model=..., tools=[submit_review])` is built fresh per `review()` call (no compile/correctness loop — `submit_review` is the only tool by default) → `Runner.run(..., max_turns=4)`. The submit tool replaces the `output_type=Pydantic` enforcement that the SDK used to translate to a `response_format=json_schema` API field — that field is rejected by reasoning-model providers (DeepSeek-reasoner, etc.), so the Reviewer routes its structured submission through a tool call instead. Tool-call schemas are universally supported across OpenAI-compatible providers; the same Pydantic validator runs inside the tool body, preserving the "validation failure → in-loop retry" guarantee. Strict Pydantic validation on `bottleneck_classification` (`Literal["memory_bound", "compute_bound", "balanced"]`) and `branch_quality` (`BranchQuality` enum) surfaces hallucinated values as in-loop tool errors.

- `submit_review(outcome, bottleneck_classification, branch_quality, metric_deltas=None, bottleneck_diagnosis="", suggestions=None, conditional_assessment="")` — required Python args (`outcome`, `bottleneck_classification`, `branch_quality`) match `ReviewerFeedbackOutput`'s required Pydantic fields; optional args with defaults match the Pydantic-optional fields. The tool body instantiates `ReviewerFeedbackOutput(...)` (triggering validation) and stores the result in a per-call captured dict. On validation failure the tool returns `submit_review FAILED:<error>` so the SDK hands the error back to the LLM as the tool-call response, prompting an in-loop retry within the turn budget.
- Tool registered with `function_tool(_make_submit_review_tool(...), strict_mode=False)`: the SDK's strict-schema validator rejects `dict[str, X]` (the `metric_deltas` arg) with the same `additionalProperties should not be set` UserError that originally killed the `output_type=Pydantic` path. `strict_mode=False` skips that pre-flight check; Pydantic still validates inside the tool body, so end-to-end type safety is preserved and malformed payloads bounce through the in-loop retry budget.
- `max_turns=4` reserves room for one in-band validation retry, mirroring the Planner.
- `MaxTurnsExceeded` recovery: the captured dict is preferred — if a valid submission landed before the budget ran out, it's converted to `ReviewerFeedback` and returned. If the dict is empty, the rule-based fallback is invoked with `error_reason="max_turns_exceeded"`.

**Output models**:
- `ReviewerFeedbackOutput` (Pydantic) — validated inside `submit_review`'s tool body.
- `ReviewerFeedback` (dataclass) — internal representation. Adds `degraded: bool` and `error_reason: str` so the orchestrator can surface/halt when a run came from retry exhaustion rather than a healthy LLM call. `BranchQuality` is a `str`-subclass enum defined in this module.

**Prompt assembly**: `build_user_prompt()` (static method) — sections, in order: Current kernel (with backtick escaping), **Run context** (once-per-run bottleneck via shared `render_run_context()` helper — always present for the Reviewer, since it's invoked only after the orchestrator has a `run_bottleneck`), Profiling summary, Scoring (SOL score, headroom %), optional Search tree context, optional **Siblings already tried from this parent** (rendered between `## Search tree context` and `## Knowledge base context`, omitted when the `sibling_context` kwarg is empty), optional Knowledge base context. Empty sections are omitted. Both the iter=0 baseline-review path and the per-iter Reviewer path receive **condensed** source via `Kernel.render_condensed_source(representative_workload_uuid=workloads[0].uuid)`. The Coder is the only agent that gets verbatim source (because it must edit the autotune decorator).

The `sibling_context: str = ""` kwarg on both `build_user_prompt()` and `review()` carries the rendered per-sibling one-liners from `SearchTree.render_siblings(parent.id, exclude_id=child.id)` — the current child is excluded so the Reviewer sees only its true peers. Default empty preserves call sites without sibling history; section gating is `if sibling_context:`.

**Input** (via orchestrator): `kernel_source`, `profiling_summary`, `sol_score`, `headroom_pct`, `bottleneck: BottleneckType` (once-per-run classification from `classify_run`), `tree_context=""` (root-to-child trajectory from `SearchTree.render_path`), `kb_context=""` (reserved for future Reviewer KB), `prev_sol_score=None`, `profiling: ProfilingResult | None = None` (renders the analytical + NCU blocks in the profiling summary when supplied; `profiling.analytical` itself is `AnalyticalMetrics | None`, and the renderer guards reads via `profiling.has_analytical`), `sibling_context: str = ""` (rendered sibling history from `SearchTree.render_siblings(parent.id, exclude_id=child.id)`). The Reviewer is also invoked at iter=0 by the orchestrator's Phase-A baseline-review pass with `prev_sol_score=None` to seed `root.last_review` / `root.branch_quality` (the rule-based fallback already handles `prev_sol_score=None` → outcome="neutral", BLOCKED_POTENTIAL; the LLM prompt path doesn't take `prev_sol_score` so framing is unchanged).

**Profiling-summary rendering (`render_profiling_summary`)**: emits up to two blocks. The `### Analytical (roofline)` header is rendered whenever `profiling.has_analytical` *or* a `roofline` is supplied — AI / ridge_point come from `RooflineResult` (run-level invariant), independent of `analytical`. The achieved / pct_peak lines are rendered only when `profiling.has_analytical` is True; when `analytical is None` (per-iter byte count couldn't be derived), the renderer appends the placeholder line `- achieved / pct_peak: [unavailable — no byte count]` in their place so the Reviewer sees an explicit "missing signal" cue rather than inferring zero. The `### NCU (curated)` block renders unchanged when NCU data is present, or surfaces a `[DEGRADED: NCU unavailable — reason=…]` notice when `profiling.degraded` is set. The Reviewer always fires when `profile_kernel` produced any `ProfilingResult` (the orchestrator's guard is on `profiling is None`, not on a `flops/nbytes > 0` gate — `profile_kernel` accepts `nbytes=0` by returning `analytical=None` while still running NCU).

**Rule-based fallback**: `rule_based_feedback()` derives feedback from the sol delta alone when no LLM is configured **or** when the SDK loop fails to produce a valid submission. In all degraded paths the result is stamped `degraded=True` with one of these `error_reason` tags so the orchestrator can distinguish causes:
- `llm_retries_exhausted` — `run_agent` returned `None` after all transient retries.
- `max_turns_exceeded` — SDK raised `MaxTurnsExceeded` and no valid submission was captured before the budget ran out.
- `missing_submit_review` — the SDK loop ended cleanly (within `max_turns`) but the LLM never invoked `submit_review`.
- `model_behavior_error:<ExcType>` — the OpenAI Agents SDK's `ModelBehaviorError` was raised inside `Runner.run` (typically because the LLM emitted a tool call for a tool that isn't registered, e.g., a stale prompt mention of `query_metric` after a prompt-template change). The defensive catch in `ReviewerAgent.review()` degrades to rule-based fallback with this tag instead of letting the exception unwind `Orchestrator.run()` and crash the entire optimization. The `<ExcType>` part is the exception class name (currently `ModelBehaviorError`).

The orchestrator logs a warning for any non-empty `error_reason`, distinguishing all four from the expected "no-LLM" configuration (where `error_reason` stays empty).

**Branch quality values**: `promising`, `blocked_potential`, `plateau`, `dead_end`.

**Specialization hook**: `prompt_dir` is a constructor parameter, so a future Compute-Reviewer / Memory-Reviewer split can swap in specialized system prompts without subclassing.

**System prompt assembly (split + conditional)**: The Reviewer's system prompt is split into two files in `src/prompts/reviewer/`:
- `system.md` — the always-on base instructions (read into `ReviewerAgent._instructions_base` at agent construction). Contains zero mentions of `query_metric` or the metric menu.
- `system_metric_queries.md` — the addendum describing the multi-turn `query_metric` tool, its expected arguments, the operating procedure, and the metric-menu format. Read into `ReviewerAgent._instructions_metric_queries` at construction (always loaded, even when the flag is off — small cost).

Conditional assembly happens inside `ReviewerAgent.review()`: when `ACTSConfig.reviewer_metric_queries=True`, the addendum is appended to `_instructions_base` and passed as the agent's system prompt; when `False` (default), only `_instructions_base` is used. This mirrors exactly the gate that controls `query_metric` tool registration — preventing the prompt-leak regression where the LLM tried to call `query_metric` even when the tool wasn't registered (which crashed the orchestrator with `agents.exceptions.ModelBehaviorError`). A back-compat alias `_instructions = _instructions_base` is kept so callers/tests reading the old field name still work.

**Diagnostic rules in `system.md`**: rule blocks in `src/prompts/reviewer/system.md` constrain the LLM's classification logic beyond the Pydantic schema — read the prompt for the full text; the doc only acknowledges they exist so future readers know where to look. The "What you receive" list also splits `Search tree context` (root-to-current path) and `Siblings already tried from this parent` (peer evidence) into two items — the sibling line names itself as the evidence base for the repeated-pathway dead_end row in the branch-quality table, closing the prior contract-drift gap where siblings were mentioned in rules without being passed to the prompt.
- **Launch-bound guard**: banded interpretation of the analytical `pct_peak: bw <Y>%` value. `< 5%` ⇒ kernel is launch-bound on this workload (occupancy is not the lever — fixed launch cost dominates); `[5%, 50%]` ⇒ partially launch-amortized (occupancy may be a lever but not necessarily); `> 70%` ⇒ near the memory ceiling (occupancy gains won't translate; fusion / precision / L2-reuse are the remaining levers). In every band, occupancy-targeting suggestions must be tied to a specific stall metric, not to a low occupancy number alone.
- **Regression-row rewrite for `dead_end`**: `dead_end` requires *either* an absent `conditional_assessment` pathway *or* a repeated-pathway failure already on the tree-context failed-action list. A regression with a non-empty `conditional_assessment` pathway that has not already failed on an ancestor / sibling is `blocked_potential`, not `dead_end`.
- **Regression-polarity rules** (new subsection, four numbered rules): fire whenever this iter's SOL < parent's SOL (any negative delta — threshold-independent, distinct from the −0.02 cut that drives the verdict).
  1. Same-action-ID param suggestions are allowed **only** when `bottleneck_diagnosis` cites a specific metric movement and ties it to the parameter being changed; without a metric chain, the Reviewer diagnoses only and leaves `suggestions` symptom-focused.
  2. When no metric→param tie is available, `conditional_assessment` describes what *class* of move would unlock progress — never "tune this action's space further."
  3. Banned phrases on regression iters: "action space is still wide open", "only one configuration has been tried", and any action-class name followed by "further" / "more" / "different" without an accompanying metric chain in the same suggestion. These were the exact promote-the-class wordings that bypassed the verdict heuristic in pre-design postmortems.
  4. If the same `action_applied` ID has regressed on a sibling AND on this iter, the verdict MUST be `dead_end` — this grounds the existing repeated-pathway row of the branch-quality table now that sibling evidence is actually surfaced to the Reviewer.
- **Anti-pattern "Prescribe a fix on a regression without a metric chain"**: a regression with diagnosis-only suggestions is the correct shape; a regression with "try a different param" suggestions and no metric→param tie is the polarity bias this rule guards against.

**Model choice**: Can be cheaper model (analysis is easier than planning).

**Private surface**:
- `_make_submit_review_tool(captured: dict) -> Callable[..., str]` — closure factory that returns the `submit_review` tool body bound to a per-call captured dict. The tool body validates `ReviewerFeedbackOutput(**kwargs)`; on success it stores the validated output in `captured` and returns a sentinel string for the LLM to confirm; on failure it returns `submit_review FAILED:<error>` so the SDK hands the error back for in-loop retry. Factory is unit-testable without the SDK.
- `_render_review_for_planner(fb: ReviewerFeedback | None) -> str | None` — module-level helper used by the orchestrator to convert a parent node's `last_review` into the string passed to the Planner's `reviewer_feedback` slot. Renders a curated subset (outcome / bottleneck_diagnosis / suggestions / conditional_assessment) and skips fields the Planner already has from other channels: `metric_deltas` (Planner has the profiling summary), `bottleneck_classification` (Planner has `run_bottleneck`), and `branch_quality` (search-engine concern, not planning input). Returns `None` for `None` input so the Planner's prompt-section guard (`if reviewer_feedback:`) cleanly omits the section on iter-1 root expansion when no baseline review has run.
- `has_model` property — `self._model is not None and _SDK_AVAILABLE`. Returns `False` even when a model stub is attached if the SDK isn't importable, so callers branch correctly without touching `_model` directly.
- `parse_feedback` removed — Pydantic validation runs inside the tool body, so no out-of-loop parser is needed.

**Multi-turn metric queries (opt-in)**

The Reviewer can be promoted from the default submit-only shape into a bounded multi-turn shape that lets the LLM pull additional NCU metrics on demand, instead of receiving the full `raw_metrics` dict up front in the curated profiling summary.

- **Flag**: `ACTSConfig.reviewer_metric_queries: bool` — defaults to `False`. Lives in INI under `[search]` as `reviewer_metric_queries = false`. Off by default so the existing submit-only shape stays the canonical path; flipping it on is the only change needed to enable on-demand fetches.
- **What activating it changes**: tool registration grows from `[submit_review]` to `[submit_review, query_metric]`, the SDK turn budget goes from `max_turns=4` to `max_turns=6` (room for a fetch-then-submit round-trip on top of the existing one in-band validation retry), and `build_user_prompt()` appends metric menus. `## Available metric groups (queryable)` summarizes grouped diagnostic inventories from `ProfilingResult.metric_groups`; `## Available raw metrics (queryable)` lists exact `ProfilingResult.raw_metrics` keys.
- **`query_metric(names: list[str]) -> dict[str, str]`** — argument is a list of exact metric names and/or group names encoded as `"group:<name>"`. Exact metric values are stringified floats for known names; unknown names map to `"[unknown]"`; if the iteration's `raw_metrics` is empty exact queries return `"[no data]"`. Group queries return flattened keys like `group:tensor_core.<metric>` with values `present: <value>` or `missing`, so missing metrics are never confused with real zeroes. The LLM is expected to read the curated summary first and only `query_metric` for genuinely missing signals before calling `submit_review`.
- **Strict-mode opt-out**: registered via `function_tool(_make_query_metric_tool(...), strict_mode=False)` for the same reason the Planner / Reviewer submit tools opt out — the SDK's strict-schema validator rejects `list[str]` and `dict[str, X]` arg types with the `additionalProperties should not be set` UserError. See JOURNAL.md "2026-04-26 — strict_mode=False fix" for the full rationale; type safety is preserved because `query_metric` does its own input handling inside the tool body.
- **Failure-mode inheritance**: no new degraded `error_reason` tags and no new exception types. The multi-turn shape reuses the existing `max_turns_exceeded` / `missing_submit_review` / `llm_retries_exhausted` triplet — `max_turns_exceeded` now covers both "ran out of turns mid-validation-retry" and "ran out of turns after too many `query_metric` calls" without needing a new tag, and `missing_submit_review` still fires identically when the loop exits cleanly without a submission.
- **Operating procedure**: the LLM-facing contract — when to read curated metrics versus when to fetch, and the expected single-fetch-before-submit pattern — lives in `src/prompts/reviewer/system.md`. Treat the curated summary as primary; treat `query_metric` as the exception path.

## Why Debugger Was Merged Into Coder

With the Coder having compile + correctness tools, a separate Debugger was redundant. A compilation error that previously took 3 LLM calls (Coder → Debugger → Coder) now resolves in one Coder call with an internal tool loop. Failed branches are handled by the tree search (pruning), not by escalating to a separate agent.

See JOURNAL.md "Debugger merged into Coder (2026-04-13)" for full rationale.
