# Python 3.12 production venv (`~/.venvs/acts_run_venv`)

The venv ACTS uses for live runs and integration tests against SOL-ExecBench
library types. Required because SOL pins `requires-python = ">=3.12"`. The
older `~/.venvs/acts_test_venv` (Python 3.10, no torch) stays for torch-less unit
tests.

Host: Ubuntu 20.04, NVIDIA RTX 6000 Ada, driver 570.172.08, CUDA 12.8.

**Before you run the recipe**, set `SOL_EXECBENCH_PATH` and `SOLAR_PATH`
to your local checkouts:

```bash
export SOL_EXECBENCH_PATH=/path/to/SOL-ExecBench
export SOLAR_PATH=/path/to/SOLAR
# Author's machine:
#   SOL_EXECBENCH_PATH=/home/hel19/workspace/projects/self-evolved-llm/repo/benchmark/SOL-ExecBench
#   SOLAR_PATH=/home/hel19/workspace/projects/self-evolved-llm/repo/benchmark/SOLAR
```

## Setup recipe

`uv` provides Python 3.12 in userspace — no `sudo` / no deadsnakes PPA.

```bash
# 1. Create venv (uv auto-fetches CPython 3.12 if missing).
uv venv --python 3.12 ~/.venvs/acts_run_venv

# 2. Install torch + torchvision from the cu128 wheel index.
VIRTUAL_ENV=~/.venvs/acts_run_venv uv pip install \
    "torch>=2.10" "torchvision>=0.24" \
    --index-url https://download.pytorch.org/whl/cu128

# 3. Install SOL-ExecBench editable, dependencies skipped.
VIRTUAL_ENV=~/.venvs/acts_run_venv uv pip install \
    -e "$SOL_EXECBENCH_PATH" \
    --no-deps

# 4. Install the SOL deps that ACTS actually uses.
VIRTUAL_ENV=~/.venvs/acts_run_venv uv pip install \
    pydantic safetensors click rich pyyaml pytest pytest-asyncio

# 5. Install the OpenAI Agents SDK (drives Coder/Planner/Reviewer agents).
#    Without this, ``src.agents.llm_backend._SDK_AVAILABLE`` is False and
#    every live run aborts in the baseline generator with
#    ``BaselineGenerationError: No model configured``.
#    ``httpx[socks]`` pulls in ``socksio`` so the OpenAI client's httpx
#    transport can negotiate a SOCKS proxy when the operator's shell has
#    ``ALL_PROXY=socks5://...`` set (otherwise ``AsyncOpenAI.__init__``
#    raises ``ImportError: Using SOCKS proxy, but the 'socksio' package
#    is not installed`` and the run aborts before iter 0).
VIRTUAL_ENV=~/.venvs/acts_run_venv uv pip install openai-agents 'httpx[socks]'

# 6. Install SOLAR + torchview. SOLAR drives the 4-stage T_SOL pipeline
#    consumed by ``src.benchmark.solar_adapter.derive_t_sol``. Without it,
#    ``_load_sol_problem`` fails fast with an actionable error — the
#    builtin fallback yields ``t_sol_us=0.0`` on SOL specs (zero
#    flop_count / memory_bytes), which would silently corrupt every score.
VIRTUAL_ENV=~/.venvs/acts_run_venv uv pip install torchview
VIRTUAL_ENV=~/.venvs/acts_run_venv uv pip install \
    -e "$SOLAR_PATH" \
    --no-deps

# 7. Install flashinfer (external reference baseline, Option C). Pinned to
#    0.6.12 to match the wrapper sources extracted from the mit-han-lab-kda
#    contest repo (its requirements.txt hard-pins flashinfer-python==0.6.12,
#    the BatchMLAPagedAttentionWrapper API reference_flashinfer.py targets).
#    Ada sm_89 compatible. See
#    doc/specs/2026-06-03-external-reference-baseline-design.md.
#
#    GOTCHA — re-pin torch in the SAME resolve. flashinfer-python's metadata
#    requires `torch==2.10.0` and a CUDA-13 toolkit chain; installing it bare
#    silently downgrades the cu128 torch 2.11 to 2.10.0 and swaps
#    cuda-toolkit 12.8.1 -> 13.3.0 / cudnn / nccl (observed 2026-06-03). Pass
#    the cu128 torch pin + index alongside flashinfer so the resolver keeps
#    torch 2.11.0+cu128 pinned while still installing flashinfer's own
#    cu13 JIT/cubin helper deps (cuda-tile, nvidia-cutlass-dsl, nvidia-nvvm,
#    nvidia-cuda-nvcc==13.3.x, apache-tvm-ffi, einops, ninja, tabulate).
#    Those coexist with torch's bundled nvidia-cuda-runtime-cu12==12.8.90 —
#    flashinfer uses them only for its kernel JIT path; GPU ops on the cu128
#    torch stack stay intact. (If you instead install flashinfer bare and the
#    torch downgrade happens, recover with step 2's cu128 torch line.)
VIRTUAL_ENV=~/.venvs/acts_run_venv uv pip install \
    "flashinfer-python==0.6.12" \
    "torch>=2.11" "torchvision>=0.24" \
    --index-url https://download.pytorch.org/whl/cu128 \
    --extra-index-url https://pypi.org/simple

# Verify: flashinfer imports and torch is still cu128 2.11.
~/.venvs/acts_run_venv/bin/python -c "import torch; from flashinfer.mla import BatchMLAPagedAttentionWrapper; import flashinfer; print('flashinfer', flashinfer.__version__, '| torch', torch.__version__)"
# expected: flashinfer 0.6.12 | torch 2.11.0+cu128

# 8. Prepend cuda bin to the venv's activate script so ``ncu`` is on PATH.
#    Without this, ACTS's profiler subprocess discovery falls back to a
#    hardcoded ``/usr/local/cuda-12.8/bin/ncu`` path; clean PATH delivery
#    via activate keeps the recipe self-sufficient and matches the
#    convention used by other CUDA-bound venvs on this host.
echo 'export PATH="/usr/local/cuda-12.8/bin:$PATH"' \
    >> ~/.venvs/acts_run_venv/bin/activate

# Verify: after re-sourcing activate, ``ncu`` resolves to the cuda-12.8 bin.
source ~/.venvs/acts_run_venv/bin/activate
which ncu   # expected: /usr/local/cuda-12.8/bin/ncu
```

## Optional: enable clock-locking

This is **host-level operator setup**, not an ACTS code change. Do it once
per machine. ACTS runs correctly without it; the section explains what you
gain by configuring it.

### Why it matters

NVIDIA GPUs auto-tune SM/memory clocks based on thermal headroom and power
budget. Across iterations of the same kernel, boost-clock variance can swing
benchmark latency by **5–15%**. With clock-locking active, latencies are
reproducible across iterations and across whole runs. Without it, ACTS's
plateau-termination heuristic (which compares iteration-N latency against
the running best) can fire spuriously on clock-jitter noise rather than on
real performance plateaus.

### Failure mode today

On a fresh host, `src/pipeline/optimize.py` invokes SOL-ExecBench's
`probe_clock_lock_available()` at run start. If the probe fails — typically
because `nvidia-smi -lgc` requires `sudo` and the user has no NOPASSWD
entry — ACTS emits a `clock_lock_unavailable` event with the reason in the
payload (e.g. `"no sudo or unsupported GPU"`). The run continues normally;
clocks are simply not pinned. Latency measurements remain valid, just
noisier across iterations.

### Options to enable (most → least recommended)

#### 0. Prerequisite: enable `nvidia-persistenced` (required for verify to pass)

```bash
sudo systemctl enable --now nvidia-persistenced
```

Persistence mode pins `clocks.applications.{graphics,memory}` at the lock
target between `nvidia-smi -lgc/-lmc` and the verify read; without it the
GPU drops to idle clocks (~810 MHz DRAM on RTX 6000 Ada) the moment the
lock subprocess exits, and `_verify_gpu0_locked` in
`src/pipeline/optimize.py` mismatches the expected target and rolls back
the partial lock with `verify_failed`. The lock is issued correctly —
it just doesn't stick.

`enable --now` both starts the service immediately *and* configures it to
start on every boot. The latter half is the load-bearing part: a 2026-05-07
reboot lapsed clock-locking on this host because persistenced wasn't
enabled-at-boot at the time, and the next ACTS run silently fell back to
unlocked-clocks even though the sudoers entry was intact.

##### Verify

```bash
systemctl is-active nvidia-persistenced
# Expected: active

nvidia-smi --query-gpu=persistence_mode --format=csv
# Expected:
#   persistence_mode
#   Enabled
```

If `nvidia-smi -lgc` prints
`Warning: persistence mode is disabled on device 00000000:99:00.0`,
persistenced is not running — that warning was the empirical signal during
2026-05-08 diagnosis of the silent verify-failed rollback. The lock command
exits 0 (NVML accepts it), but the subsequent verify reads idle clocks and
unwinds the partial lock.

This is *additive* to options 1–3 below, not a replacement — you still need
a way for ACTS to invoke `sudo nvidia-smi -lgc` non-interactively.

#### 1. Passwordless `sudo` for `nvidia-smi` (recommended)

Add a sudoers drop-in for the user that runs ACTS. The rule grants
*passwordless* `sudo` for `nvidia-smi` only — no other binaries, no
broader sudo capability. Tightest possible scope.

##### Step 1 — verify your username and `nvidia-smi` path

```bash
echo "$USER"            # expected: hel19 (or whichever account runs ACTS)
which nvidia-smi        # expected: /usr/bin/nvidia-smi
```

If `which nvidia-smi` returns a different path (e.g.
`/usr/local/cuda-12.8/bin/nvidia-smi`), use that path in step 3 instead.

##### Step 2 — open `visudo` with a dedicated drop-in file

```bash
sudo visudo -f /etc/sudoers.d/acts-clock-lock
```

`visudo` is the *only* safe way to edit sudoers files — it validates
syntax before saving, so a typo refuses-to-save instead of locking you
out of `sudo`. **Never edit sudoers files with a regular editor.**

The drop-in directory `/etc/sudoers.d/` is auto-included by the main
`/etc/sudoers`, so the main file stays untouched. The filename
`acts-clock-lock` is just a tag — pick anything *without* a `.` or `~`
in the name (those get ignored).

##### Step 3 — add exactly one line, then save

```
hel19 ALL=(root) NOPASSWD: /usr/bin/nvidia-smi
```

Anatomy:

- `hel19` — username this rule applies to. Replace with your `$USER`.
- `ALL` — host scope. `ALL` = any host (irrelevant for a single machine,
  this is just standard sudoers syntax).
- `(root)` — the user the listed commands may be run as. `(root)` means
  "you can run the commands below *as root*."
- `NOPASSWD:` — skip the password prompt for the listed commands. The
  trailing `:` is mandatory.
- `/usr/bin/nvidia-smi` — the **only** command this no-password rule
  permits. No wildcards, no other binaries.

Save and exit (`:wq` in vim, `Ctrl-O` then `Ctrl-X` in nano). If
`visudo` says "syntax error", it offers to re-edit; fix the typo and
try again.

##### Step 4 — tighten file permissions

```bash
sudo chmod 0440 /etc/sudoers.d/acts-clock-lock
```

`0440` = readable by root and the `root` group, no one else, no write
or execute. `visudo` usually sets this automatically, but a stricter
chmod is harmless and a sanity check. Files in `/etc/sudoers.d/` with
broader permissions are *ignored entirely* by sudo, which is a silent
failure mode — verify.

##### Step 5 — verify the rule works without prompting

```bash
# All four MUST run without prompting and without printing
# "sudo: a password is required". Together they exercise read access
# (-q -d CLOCK), write access (-lgc / -lmc), and reset (-rgc / -rmc).
sudo -n nvidia-smi -q -d CLOCK | head -5
sudo -n nvidia-smi -lgc 2505,2505 -i 0
sudo -n nvidia-smi -lmc 10001 -i 0
sudo -n nvidia-smi -rgc -i 0
sudo -n nvidia-smi -rmc -i 0
```

The `-n` flag means "non-interactive — never prompt." If sudo prints
"a password is required," the rule isn't matching. Most common causes:
typo in username, wrong path to `nvidia-smi`, file permissions other
than `0440`.

The clock values shown above (`2505,2505` SM clock + `10001` memory)
are the design-boost target on RTX 6000 Ada — they match
`configs/arch/RTX6000Ada.yaml`'s `freq_GHz=2.505` so SOLAR T_SOL stays
calibrated. For other hosts:

```bash
# List supported (memory, graphics) pairs and pick a value that
# matches your arch YAML's freq_GHz.
nvidia-smi -q -d SUPPORTED_CLOCKS | head -60
```

Avoid locking to the max overclock (`Max Clocks` in `nvidia-smi -q -d
CLOCK`). Sustained ACTS runs are a long thermal-pressure series; an
overclock will silently throttle mid-run, reintroducing the variance
you locked clocks to remove. Stay at or near the design-boost clock.

##### Step 6 — undo (if you ever want to remove the rule)

```bash
sudo rm /etc/sudoers.d/acts-clock-lock
```

A single deletion fully reverts. No reboot needed.

##### What this DOESN'T do (security boundary)

- Doesn't grant any other root capability — `sudo bash`, `sudo apt
  install`, etc. all still prompt for password.
- Doesn't make ACTS run as root — your Python process still runs as
  your user; it just shells out to `sudo -n nvidia-smi` internally.
- Doesn't affect other users on the host — only the named user matches
  the rule.

#### 2. Run ACTS as `root`

Quick but undesirable: every ACTS subprocess (the agent SDK, the compiled
kernel, pip if a run installs anything) inherits root. Mention only as a
last-resort workaround on locked-down machines where editing sudoers is not
permitted. **Not recommended as the default path.**

#### 3. `nvidia-modprobe` SUID (situational, not always sufficient)

Some setups grant per-user GPU access via `nvidia-modprobe` with the SUID
bit set:

```bash
sudo chmod u+s /usr/bin/nvidia-modprobe   # if the package is installed
```

Caveat: `nvidia-modprobe` primarily governs device-node creation and
performance-counter access, not `nvidia-smi -lgc`. On driver 570.x and
recent CUDA 12.x stacks, SUID-`nvidia-modprobe` alone is **not reliably
sufficient** to enable clock-locking — you still hit the sudo gate inside
`lock_clocks`. Flag this as "may help on some driver versions" rather than
a clean recommendation. Prefer option 1.

### Verify clock-locking is available

After applying one of the options above, confirm from inside the ACTS venv:

```bash
~/.venvs/acts_run_venv/bin/python -c "
from sol_execbench.core.bench.clock_lock import probe_clock_lock_available
ok, reason = probe_clock_lock_available()
print('available:', ok)
print('reason:', reason)
"
```

Expected output when enabled:

```
available: True
reason: ok
```

If `available: False`, the `reason` string explains why (e.g.
`no sudo or unsupported GPU`, `nvidia-smi not on PATH`). Re-check the
sudoers entry and the `sudo -n nvidia-smi -lgc` smoke test above.

### What ACTS does on the failure path

When the probe returns `False`, ACTS does not abort. The pipeline:

1. Emits a `clock_lock_unavailable` event (visible in the run's event
   stream) with the probe's reason in the payload.
2. Skips the `lock_clocks` call entirely.
3. Still registers `_unlock_clocks_safe` (in `src/pipeline/optimize.py`)
   via `atexit` — on a never-locked run this is a no-op, which is the
   intended behavior (no spurious `nvidia-smi -rgc` invocation at exit).
4. Proceeds with benchmarking. Measurements are valid; iteration-to-
   iteration variance is just higher than on a clock-locked host.

In short, an unlocked run produces correct results with noisier latencies.
Enable clock-locking when you want plateau detection and cross-run latency
comparisons to be tight; skip it if the host doesn't permit the sudoers
edit and you're willing to tolerate a few percent of timing noise.

## Optional: enable NCU performance counters for non-admin users

Like clock-locking, this is **host-level operator setup**, not an ACTS
code change. Do it once per machine. ACTS runs correctly without it; this
section explains what you gain by configuring it.

### Why it matters

NCU (NVIDIA Compute Profiler) is what gives the Reviewer per-kernel
diagnostic metrics — achieved occupancy, L2 hit rate, DRAM throughput,
top warp stalls (long_scoreboard, short_scoreboard, imc_miss), tensor-core
utilization. Without these, the Reviewer falls back to the analytical
roofline alone, which only tells you "memory-bound vs compute-bound" at a
coarse level. With them, the Reviewer can reason concretely: "67% L2 hit
rate, dominant long_scoreboard stall — try L2-aware tiling" or "8%
occupancy, low TC util — block size is wrong."

### Failure mode today (default driver state)

Modern NVIDIA driver releases ship with the kernel module flag
`NVreg_RestrictProfilingToAdminUsers=1` by default. Under this flag,
`ncu` (and other CUPTI-based profilers) returns `ERR_NVGPUCTRPERM` for
any non-root user — the GPU performance counters are admin-only at the
kernel level. ACTS's profiler subprocess captures this as
`ncu_skipped:permanently_unavailable:nvgpuctrperm` in the run log; the
analytical roofline still computes, but `top_stalls` is `[]`,
`achieved_occupancy` is unreported, and the Reviewer's `query_metric`
tool returns `[no data]` for any NCU-sourced key.

### How to enable

The fix is a kernel module parameter change, applied at boot. Two
commands plus a reboot.

##### Step 1 — write the modprobe drop-in

```bash
echo 'options nvidia "NVreg_RestrictProfilingToAdminUsers=0"' | \
    sudo tee /etc/modprobe.d/nvidia-counters.conf
```

What this does:

- `echo 'options nvidia "NVreg_RestrictProfilingToAdminUsers=0"'`
  produces one line in modprobe's standard syntax:
  `options <module-name> <param>=<value>`. It tells the kernel: "when
  loading the `nvidia` module, set `NVreg_RestrictProfilingToAdminUsers`
  to `0`."
- `| sudo tee /etc/modprobe.d/nvidia-counters.conf` writes that line to
  a new file. (`tee` runs under `sudo` and can write root-owned files;
  shell redirection `>` would not, because redirection runs as your
  user before sudo gets involved.)
- The file's job is to *persist* the parameter across reboots. The
  kernel scans `/etc/modprobe.d/*.conf` for any module named in those
  files when loading.

##### Step 2 — rebuild initramfs

```bash
sudo update-initramfs -u
```

The initramfs ("initial ram filesystem") is a tiny filesystem image the
bootloader loads *before* the real root filesystem mounts. It contains
kernel modules and a snapshot of `/etc/modprobe.d/` so module-load
options are honored at very early boot. `update-initramfs -u`
regenerates that image for the running kernel, baking the new
`nvidia-counters.conf` into it.

Whether you actually need this step depends on when `nvidia` loads on
your machine — on most Ubuntu desktop installs it loads later in boot
(systemd / udev), where the live `/etc/modprobe.d/` is already mounted.
On systems where `nvidia` is in initramfs (early-console use, some
Wayland sessions), the kernel reads the initramfs snapshot and not the
live filesystem. Cheap belt-and-suspenders: harmless if not needed,
essential if it is. NVIDIA's own docs include the step.

##### Step 3 — reboot

```bash
sudo reboot
```

The change is read at module-load time, which only happens at boot
(or via a fragile `rmmod nvidia*` + `modprobe nvidia` cycle that
typically fails because something on the system is holding a CUDA
context). Reboot is the supported path.

##### Step 4 — verify after reboot

```bash
# 1. Kernel parameter is what we set:
cat /proc/driver/nvidia/params | grep RmProfilingAdminOnly
# Expected: RmProfilingAdminOnly: 0

# 2. ncu can actually capture counters as a non-root user:
ncu --print-summary none --target-processes all \
    --launch-skip 0 --launch-count 1 \
    ~/.venvs/acts_run_venv/bin/python -c "
import torch
x = torch.randn(1024, device='cuda')
y = x * 2
torch.cuda.synchronize()
"
# Expected: ncu prints a metrics table (no ERR_NVGPUCTRPERM,
# no "User does not have permission to access the GPU performance
# counter" message).
```

If step 1 still shows `RmProfilingAdminOnly: 1`, the modprobe drop-in
didn't take effect — most common cause is a typo in the file path or
the file having the wrong permissions. Re-check `cat
/etc/modprobe.d/nvidia-counters.conf` and make sure it contains exactly
`options nvidia "NVreg_RestrictProfilingToAdminUsers=0"`.

##### Step 5 — undo (if you ever want to revert)

```bash
sudo rm /etc/modprobe.d/nvidia-counters.conf
sudo update-initramfs -u
sudo reboot
```

After the reboot, `RmProfilingAdminOnly` returns to its default value
(`1`), and `ncu` once again rejects non-root invocations.

### What ACTS does on the failure path

When `ncu` fails for any reason (admin restriction, missing binary,
permission-class error, transient driver issue), ACTS does not abort.
The analytical roofline (HardwareSpec peaks + workload FLOPs/bytes)
still computes — that's the *required, fail-closed* path. The NCU
subprocess is *best-effort* and degrades gracefully:

1. The first failure is classified by signature (e.g.
   `nvgpuctrperm`, generic non-zero exit). Permanent failure
   signatures cache a module-level flag so subsequent calls
   short-circuit and don't re-fork `ncu`.
2. The roofline gets a `DEGRADED` tag in events
   (`ncu_skipped:permanently_unavailable:<sig>` for the cached path,
   `ncu_nonzero_exit:<rc>:<stderr-fingerprint>` for transient failures).
3. The Reviewer's `query_metric` tool returns `[no data]` for any
   NCU-sourced metric key.
4. Search continues against the analytical signal alone.

In short, an NCU-disabled run produces correct results with thinner
diagnostic signal. Enable NCU when you want the Reviewer to reason
about achieved occupancy / stall classes / L2 behavior; skip it if the
host doesn't permit the kernel-module parameter change and you're
willing to lose the per-kernel measured metrics.

### Security boundary (what enabling does and doesn't do)

- **Does**: lets every local user on the system read GPU performance
  counters via `ncu` / CUPTI. There is no per-user middle setting in
  the kernel module — the flag is binary (admin-only vs all-users).
- **Doesn't**: grant any other capability. Users still can't allocate
  exclusive GPU access, change clocks, or modify driver state without
  the appropriate sudo / device permissions.
- **If you need per-user scoping** (single-tenant counter access on a
  multi-user host), gate at the `ncu` binary's filesystem permissions:

  ```bash
  sudo chgrp hel19 /usr/local/cuda-*/bin/ncu
  sudo chmod 750 /usr/local/cuda-*/bin/ncu
  # Now only hel19 (and root) can execute ncu, even though kernel-level
  # counter access is open to all.
  ```

  On a single-user dev box, layer 1 (the kernel-module flag) alone is
  enough. Layer 2 only matters on shared machines.

## Why `--no-deps`

SOL's `pyproject.toml` lists three CUDA-13-only dependencies that have no
cu12.8 wheels:

- `cuda-tile==1.1.0`
- `nvidia-cutlass-dsl[cu13]==4.4.1`
- `nvidia-cudnn-frontend==1.18.0` (cu13-paired build)

Letting pip resolve them either fails outright or pulls cu13 wheels that
crash at the first GPU op on this host. ACTS does not use the SOL features
that need cuda-tile or CUTLASS-DSL (those target Blackwell sm_100+), so we
omit them and install the rest by hand.
